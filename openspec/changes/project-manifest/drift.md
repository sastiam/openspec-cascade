## design.md

- **Labels for global OpenCode sources are hardcoded and can name the wrong folder (Major).** design.md:100 says a source is shown "as a path with `~` for the home folder and `<repo>` for the repository". design.md:107-108 read from `$XDG_CONFIG_HOME/opencode`. The code reads from `paths.xdgConfigHome` but always labels the source `~/.config/opencode` (`src/manifest/discover.ts:217` and `:224`). This label is used for both `sources` and `skipped[].source`. When `XDG_CONFIG_HOME` is outside home (for example `/tmp/cfg`), the path shown is wrong. `test/manifest/discover.test.ts:40` and `:130` lock this in: the fixture's `xdgConfigHome` is `<root>/cfg`, not `<home>/.config`, yet the test expects `~/.config/opencode/opencode.json`.
- **A plugin candidate keeps only one source (Nit).** design.md:111 says merged candidates list "all its sources". The plugin source records only the last settings file that set the key (`src/manifest/discover.ts:197`, `:203`). A plugin enabled in both `~/.claude/settings.json` and `<repo>/.claude/settings.local.json` shows only the second file in `sources`.
- **Invalid `add` flag values give an undocumented error path (Nit).** design.md:89 sends `ManifestError` and other failures to `STOPPED:`, but does not say what happens when a flag value is invalid (bad `--type`, unsafe `--check`, bad `--profile`, unknown `--host`). The code reports these as `CliUsageError`, which prints `USAGE: cascade setup: invalid entry: <path>: <zod message>`. That puts Zod's own text in the message (`src/cli/setup.ts:195-199`). design.md:57 forbids the parser's own message only for loader errors, so this path is not described anywhere.
- **Some check failures in `doctor` are rethrown, which is not described (Nit).** design.md:142 lists only timeout, `SpawnError` and non-zero exit. `src/cli/commands.ts:108-111` rethrows any other rejection from `spawner.run`. That aborts `runDoctor`, and `runSubcommand` then prints `STOPPED: doctor failed:` (`commands.ts:315-324`) instead of a per-entry check.
- **The layer object is strict, which the design does not say, and the error is misleading (Nit).** design.md:80 gives the layer only as `{"entries": [...]}`. `ManifestLayerSchema` is `.strict()` (`src/manifest/types.ts:30`). Any extra key next to `entries` fails with `<layer> layer: entries must be a list` (`src/manifest/load.ts:87`), even when `entries` is a valid list. A non-object `.openspec-cascade.json` root gives `project layer: invalid config file` (`load.ts:101`), which is also not listed.
- **Context line references are out of date (Nit).** `SUBCOMMANDS` is cited as `src/config/constants.ts:491` (design.md:9) but is at :495. The `runSubcommand` switch is cited as `src/cli/commands.ts:242-274` (design.md:9) but is at :292-326. `runDoctor` is cited as `:91-148` (design.md:12) but is at :140-198. `SubcommandDependencies` is cited as `:31` (design.md:12) but is at :35. `CascadeFileConfigSchema` is cited as `src/config/schemas.ts:483` (design.md:11) but is at :495. `isSafeVerifyCommand` is cited as `src/facade/tasks.ts:69` (design.md:14) but is at :115.
- **The header comment of `setup.ts` leaves out two actions (Nit).** `src/cli/setup.ts:2` lists only discover, show and rules, but design.md:81-87 also defines `add` and `remove`. The header comment of `commands.ts` (`src/cli/commands.ts:2`) also leaves out `spec-gate`, `lint-tasks` and the new `setup`.

## specs/project-manifest/spec.md

- **"setup writes" requirement contradicts the code (Major).** spec.md:197 says "Every file written by `setup` SHALL be written … as two-space JSON with a final line break." `setup rules --write` writes `openspec/config.yaml` as appended YAML text through `writeTextAtomic`, not JSON (`src/cli/setup.ts:245`, `src/manifest/rules.ts:16-17`). design.md:67 agrees with the code; the spec does not.
- **JSON output is pretty-printed, not compact (Nit).** spec.md:138 says `setup discover --json` "SHALL print `{"candidates":[...],"skipped":[...]}`", and spec.md:204 says `setup show --json` "SHALL print `{"entries":[...]}`". Both print indented, multi-line JSON through `JSON.stringify(value, null, MANIFEST_CONSTANTS.JSON_INDENT)` (`src/cli/setup.ts:102-104`). Tests only parse the output (`test/cli/setup.test.ts:103`, `:161`), so the literal form is neither met nor checked.
- **Discovery source labels are wrong when `XDG_CONFIG_HOME` is set (Major).** spec.md:120 and :142 ("`sources` list both files") depend on source paths being correct. For the global OpenCode files the label is always `~/.config/opencode/...`, whatever `$XDG_CONFIG_HOME` is (`src/manifest/discover.ts:217`, `:224`). Same defect as the first design.md finding.
- **Scenario "Stale project key" is only partly tested (Nit).** spec.md:104-106 requires that discovery "exits 0". The only test calls `discover()` directly and checks the result (`test/manifest/discover.test.ts:80-84`). No test runs `runSetup(["discover", ...])` with a stale `projects` key and checks the exit code. The CLI discover tests (`test/cli/setup.test.ts:154-172`) have no `~/.claude.json` fixture.
- **Scenario "Missing connector" is only partly tested (Nit).** spec.md:166-168 requires `/cascade:setup` to register a connector the user names with `setup add`. `test/plugin/setup_command.test.ts:7-16`, `:41-43` only checks that the strings `claude.ai` and `setup add` appear somewhere in `plugins/cascade/commands/setup.md`. It does not check that the ask-for-missing-helpers step (`setup.md:23`) leads to `setup add`.
